## Context

**Уведомление.** `ReminderAlarmService.buildNotif()` сейчас добавляет 3 action-кнопки («10 мин», «1 час», «2 часа»). Официальная документация Android по `NotificationCompat.Builder.addAction()` гласит, что система отображает не более 3 действий — четвёртое может быть проигнорировано системным UI. На практике часть прошивок (в т.ч. проверенная в этой сессии HyperOS) показывала ровно то количество действий, что было добавлено (наблюдали переход 2→3). Точных гарантий на 4 нет, но пользователь просит вернуть «Готово» явно с оговоркой «если можно» — добавляем четвёртой кнопкой и не блокируем это несуществующим ограничением.

**Двойное распознавание.** `AndroidSpeechHelper` в continuous-режиме держит буфер `accumulated: StringBuilder`. Когда пользователь останавливает запись (`stop()` → `listening = false; recognizer.stopListening()`), система асинхронно присылает колбэк(и) на уже остановленный `recognizer`. Наблюдаются два пути, которые НЕЗАВИСИМО могут довести до `finishContinuous()`:
- `onResults()`: `if (continuous) { appendSegment(t); if (!listening) finishContinuous() }`
- `onError()`: `if (continuous && !listening) { finishContinuous(); return }`

Если оба колбэка приходят по одному и тому же сеансу остановки (например, Google сначала шлёт `onResults` с финальным сегментом, а следом — `onError` с уже пустым/неважным кодом, или наоборot), `finishContinuous()` вызывается дважды. Первый вызов вызывает `onFinal(full)` с корректным текстом и чистит `accumulated`. Если ВТОРОЙ колбэк успевает добавить что-то в `accumulated` до своего вызова `finishContinuous()` (например, `onResults` добавляет хвостовой сегмент `t` после того, как `onError` уже отработал первым), второй `finishContinuous()` вызывает `onFinal()` ЕЩЁ РАЗ с обрывком. `RemindViewModel.onFinal` не идемпотентен — каждый вызов безусловно перезаписывает `_draft.value = text`, поэтому второй, обрывочный вызов затирает корректно распознанный черновик. `ReminderParser` не может разобрать обрывок → `preview == null` → кнопка «Сохранить» неактивна. Это воспроизводится только в облачном (онлайн) режиме, потому что `SpeechHelper` (Vosk) устроен иначе и не имеет этой пары независимых колбэков.

## Goals / Non-Goals

**Goals:**
- Уведомление показывает 4 действия: «10 мин», «1 час», «2 часа», «Готово».
- Финализация continuous-сеанса облачного распознавания происходит РОВНО один раз за сеанс, независимо от того, какой колбэк (`onResults`/`onError`) её вызвал.

**Non-Goals:**
- Не меняется поведение in-app баннера (`RingingBanner`) — там кнопка «Готово» уже присутствует с прошлой фичи.
- Не трогается `SpeechHelper` (Vosk) — по описанию пользователя офлайн-путь работает штатно.
- Не гарантируется, что 4-я кнопка отобразится на ВСЕХ устройствах/прошивках — это ограничение платформы, не баг данного изменения.

## Decisions

**Флаг `finalized` в `AndroidSpeechHelper`, а не рефакторинг структуры колбэков.**
Самое узкое и безопасное исправление: булev-флаг `finalized`, выставляемый в `true` внутри `finishContinuous()`, и проверка `if (finalized) return` в начале `finishContinuous()`. Сбрасывается в `false` в `start()` (начало нового сеанса). Это гарантирует, что вне зависимости от того, сколько раз и в каком порядке придут `onResults`/`onError` после остановки, `onFinal` наружу уйдёт максимум один раз за сеанс. Альтернатива — объединять `onResults`/`onError` в единый источник финализации через отдельный event-канал — избыточное усложнение для точечного фикса.

**4-я кнопка добавляется без дополнительной абстракции.**
Аналогично снуз-кнопкам — просто ещё один `addAction(..., "Готово", actionPi(ACTION_STOP, ...))` в `buildNotif()`, с уникальным `requestCode`.

## Risks / Trade-offs

- [4-я кнопка может не отображаться на некоторых прошивках из-за платформенного лимита в 3 действия] → Не устраняется техническими средствами (вне контроля приложения); отражено в спецификации как известное ограничение, финальную видимость проверяет пользователь на своём устройстве.
- [Флаг `finalized` не сбрасывается, если `start()` не вызывается между сеансами каким-то нестандартным путём] → `start()` — единственная точка входа в новый сеанс (`VoiceRecognizer.start()` → `cloud.start()`), сброс флага там гарантирует корректность для штатного жизненного цикла.

## Обновление по итогам проверки на реальном устройстве

**4-я кнопка подтверждённо не отображается.** На физическом устройстве (HyperOS) в уведомлении реально видно только 3 действия — 4-е («Готово») не показывается, платформенный лимит подтверждён эмпирически, а не только по документации. Решение: убрать «2 часа», оставить «5 минут», «1 час», «Готово» — ровно 3 действия, все видны.

**Двойная финализация — не единственная причина глюка при онлайн-распознавании.** После повторного тестирования (уже на пересобранном APK) поведение осталось прежним: после произнесения фразы сигнал «слушает» появляется снова, и черновик не проходит парсинг. Сравнение с `SpeechHelper` (Vosk) показало архитектурную разницу: Vosk использует один долгоживущий `SpeechService`, который сам различает промежуточный `onResult` и финальный `onFinalResult`, не пересоздавая сессию. `AndroidSpeechHelper`, наоборот, вынужден **пересоздавать** `SpeechRecognizer` после каждого обнаруженного системой молчания (это единственный способ добиться многосегментной диктовки через стандартный `RecognizerIntent.ACTION_RECOGNIZE_SPEECH`). Проблема: система Google по умолчанию считает паузу тишины завершённой всего через ~1–1.5 секунды — короче типичной паузы «договорил → потянулся нажать кнопку остановки». Из-за этого `onResults()` успевает сработать (при `listening == true`, так как пользователь ещё не нажал «стоп») и уходит в ветку «просто пауза — перезапускаем сессию», порождая слышимый повторный сигнал прослушивания, который может повторяться в цикле, пока пользователь наконец не нажмёт «стоп». Это и есть источник ощущения «глюка» — не столько повреждение данных, сколько лишние циклы перезапуска сессии, из-за которых у пользователя создаётся впечатление сбоя, вдобавок иногда закономерно приводящее к рассинхронизации накопленного текста при исчерпании ретраев (`ERROR_RECOGNIZER_BUSY` после частых пересозданий) и всплытию видимой ошибки вместо разбора черновика.

**Дополнительное решение: увеличить тайм-аут тишины.** `RecognizerIntent` поддерживает необязательные extra-параметры `EXTRA_SPEECH_INPUT_COMPLETE_SILENCE_LENGTH_MILLIS` и `EXTRA_SPEECH_INPUT_POSSIBLY_COMPLETE_SILENCE_LENGTH_MILLIS` (оба — `Long`, миллисекунды). Выставляем оба в ~3000 мс в `startSession()`. Это не гарантированный API (движок может частично игнорировать extra на некоторых прошивках), но это стандартный, документированный способ повлиять на срабатывание автопаузы, и именно он должен уменьшить частоту преждевременных перезапусков.

**Важно про предыдущую проверку.** Не исключено, что тестирование до этого момента шло на APK, собранном БЕЗ `gradlew clean` — то есть могло воспроизводить старую, ещё не пропатченную версию `AndroidSpeechHelper`/`ReminderAlarmService` из-за того же бага «грязного» инкрементального dex-мёржа, который отдельно нашли и задокументировали для `BuildConfig`. Следующая сборка и установка идут строго через `gradlew clean assembleDebug`.
